Desplegar desde cero en Coolify

Guía para instalar Coolify en un VPS nuevo de AWS y publicar el frontend Astro, la API Laravel, PostgreSQL y Redis como recursos independientes.

AWS EC2 Coolify self-hosted PostgreSQL 16 Redis Dockerfile
Antes de empezar: este procedimiento crea una instalación nueva. Si hay información que se deba conservar, realiza y descarga copias de seguridad antes de borrar el VPS o los volúmenes. Eliminar un VPS destruye sus datos locales.
Arquitectura de esta guía: los cuatro recursos se crean en el mismo servidor y destino de Docker en Coolify para que la API pueda usar las URLs privadas de PostgreSQL y Redis. No se publica ningún puerto de base de datos a Internet.

1. Preparar AWS y el dominio

Crear el VPS

  1. Crea una instancia Linux nueva. Coolify lista Ubuntu y Debian como sistemas soportados; Ubuntu LTS (por ejemplo, 24.04 LTS) es una opción práctica.
  2. Asigna una IP pública estática/Elastic IP si el proveedor lo permite, para que el DNS no cambie si la instancia se reinicia o reemplaza.
  3. Coolify publica como mínimo oficial 2 núcleos de CPU, 2 GB de RAM y 10 GB de disco libres. Eso es el mínimo de Coolify, no una garantía de recursos suficientes para compilar y operar frontend, backend y bases de datos juntos.
  4. Para este proyecto, se recomienda más memoria y CPU sostenida que el mínimo, con espacio para imágenes Docker, datos y respaldos. En instancias AWS burstable, los builds de Docker pueden agotar créditos; evita compilar frontend y backend simultáneamente o considera una instancia/build server con CPU sostenida.
  5. Conserva el acceso SSH y una copia de la clave privada. No cierres la consola del proveedor hasta validar que Coolify puede acceder al servidor.

Configurar el Security Group de AWS

Configura reglas de entrada TCP. No abras puertos de bases de datos (5432/6379) a Internet.

PuertoOrigenUso
22Tu IP pública / CIDR mínimo necesarioSSH. No lo dejes abierto a todo Internet si puedes restringirlo.
80 y 443InternetProxy de Coolify, tráfico web y certificados HTTPS.
8000, 6001, 6002Tu IP, temporalmentePanel, actualizaciones en tiempo real y terminal de Coolify al usar acceso directo por IP.

Después de configurar un dominio HTTPS para el propio panel de Coolify y confirmar que funciona, puedes cerrar 8000/6001/6002 públicamente y acceder al panel mediante el dominio. Mantén SSH abierto.

Preparar DNS

Crea registros A que apunten a la IP pública del VPS:

Nombre de ejemploDestinoUso
consultasperu.safezoneperu.comIP pública del VPSFrontend, si mantienes el dominio actual del Dockerfile Astro.
api-consultas.safezoneperu.comIP pública del VPSAPI, como está definido actualmente en la guía del backend.

Reemplaza esos nombres por tus dominios definitivos si van a cambiar. El frontend construye la URL de la API dentro del sitio estático, por lo que un cambio de dominio de API requiere actualizar el argumento PUBLIC_API_URL y volver a compilar/desplegar el frontend.

2. Instalar Coolify

  1. Conéctate por SSH al VPS como root o con un usuario que pueda usar sudo.
  2. Confirma que el Security Group permite SSH desde tu IP y que no tienes otros servicios ocupando 80/443.
  3. Ejecuta el instalador oficial de Coolify:
curl -fsSL https://cdn.coollabs.io/coolify/install.sh | bash
  1. Espera a que termine y sigue la URL indicada al final. Para acceso directo inicial normalmente es http://IP_PUBLICA:8000.
  2. Crea inmediatamente la cuenta administradora. No dejes el registro abierto: quien acceda primero puede apropiarse del panel.
  3. En Coolify, verifica que el servidor localhost esté conectado y que el proxy esté activo. Si aparece detenido, inicia el proxy antes de desplegar dominios.
  4. Guarda fuera del VPS una copia segura del archivo /data/coolify/source/.env. Incluye secretos necesarios para recuperar la instalación de Coolify.
Seguridad: el comando ejecuta el instalador oficial con privilegios de administrador. Revisa la guía vigente de Coolify antes de ejecutarlo y no compartas credenciales, claves privadas ni URLs de conexión con contraseñas.

3. Crear el proyecto y ambiente

  1. En el panel, crea un proyecto llamado Consulta Hoy Perú.
  2. Crea o selecciona el ambiente production.
  3. Usa el mismo servidor localhost y el mismo destino/red de Docker para PostgreSQL, Redis y la aplicación. La URL interna generada por Coolify solo sirve desde recursos con acceso a esa red/destino.
  4. Conecta GitHub a Coolify desde Sources si aún no has autorizado los repositorios.
Orden recomendado de despliegue: PostgreSQL → Redis → Backend → Frontend. Así las dependencias estarán listas cuando Laravel arranque y ejecute migraciones.

4. Crear PostgreSQL independiente

  1. Abre el proyecto y ambiente, elige New Resource → Databases → PostgreSQL.
  2. Selecciona el mismo servidor y destino donde vivirá la aplicación.
  3. Elige la imagen/versión PostgreSQL 16 para coincidir con la documentación del backend.
  4. Configura el nombre inicial de base de datos, por ejemplo consultahoy, o conserva los valores generados por Coolify.
  5. Guarda el usuario y contraseña generados como secretos. No reutilices contraseñas de ejemplo ni las pongas en el repositorio.
  6. Deja PostgreSQL privado: no habilites acceso público ni mapees 5432 al host. Espera a que aparezca como activo/healthy.
  7. Copia la Postgres URL (internal) de la pantalla de conexión del recurso. La usarás como DB_URL en Laravel.
  8. Configura respaldos programados desde Coolify y revisa que se guarden fuera del VPS, idealmente en almacenamiento externo.
Los valores de usuario, contraseña y base inicial se aplican cuando PostgreSQL inicializa un volumen vacío. Cambiar las variables más adelante no modifica las credenciales de una base ya inicializada. No borres el volumen para solucionar un fallo de autenticación.

5. Crear Redis independiente

  1. Elige New Resource → Databases → Redis.
  2. Selecciona el mismo servidor y destino/red de Docker.
  3. Conserva autenticación y almacenamiento persistente. Espera a que el recurso esté activo/healthy.
  4. Copia la Redis URL (internal) para usarla como REDIS_URL en Laravel.
  5. Mantén Redis privado; no publiques el puerto 6379 a Internet.

El backend usa el driver PHP phpredis, incluido en la imagen. Usar la URL interna completa permite conservar el host, puerto y contraseña generados por Coolify sin copiar manualmente datos sensibles a varios campos.

6. Desplegar el backend Laravel

Crear la aplicación

  1. En el proyecto, selecciona New Resource → Application → GitHub y el repositorio EmersonValenzuela/apiconsultasperu.
  2. Selecciona la rama main.
  3. Selecciona el método de build Dockerfile. El Dockerfile está en la raíz del repositorio; deja la ruta como /Dockerfile (o el valor predeterminado equivalente) y el directorio raíz como la raíz del repositorio.
  4. En los puertos expuestos, indica 80. No es necesario publicar un puerto del contenedor directamente en el host: el proxy de Coolify enruta el dominio al puerto interno.
  5. En Domains, asigna https://api-consultas.safezoneperu.com o el dominio que configuraste para la API.

Configurar variables de producción

Agrega las siguientes variables en la configuración de la aplicación. Marca los valores sensibles como secretos cuando Coolify lo permita.

APP_NAME="Consulta Hoy Peru"
APP_ENV=production
APP_DEBUG=false
APP_KEY=base64:REEMPLAZAR_POR_UNA_CLAVE_GENERADA
APP_URL=https://api-consultas.safezoneperu.com
LOG_LEVEL=warning

DB_CONNECTION=pgsql
DB_URL=postgres://USUARIO:CLAVE@HOST_INTERNO:5432/consultahoy

CACHE_STORE=redis
QUEUE_CONNECTION=redis
SESSION_DRIVER=redis
REDIS_CLIENT=phpredis
REDIS_URL=redis://:CLAVE@HOST_INTERNO:6379/0

CORS_ALLOWED_ORIGINS=https://consultasperu.safezoneperu.com
RATE_LIMIT_GENERAL=60
RATE_LIMIT_CALCULADORAS=30
RATE_LIMIT_RUC=20
RATE_LIMIT_DNI=5
DNI_ENABLED=false
  • Reemplaza APP_KEY con una clave recién generada. Desde una copia local del repositorio, ejecuta php artisan key:generate --show y copia el resultado completo. Nunca guardes esa clave en Git.
  • Reemplaza DB_URL y REDIS_URL por las URLs internas exactas que muestran los recursos de Coolify. No uses las URLs públicas.
  • Si la URL de PostgreSQL usa otro nombre de base de datos distinto de consultahoy, no la cambies aquí: conserva la base configurada en el recurso.
  • CORS_ALLOWED_ORIGINS debe coincidir exactamente con el origen público del frontend, incluyendo https:// y sin una barra final. Si cambia el dominio, actualiza este valor.
  • Si configuras DNI en el futuro, revisa primero las restricciones de privacidad y protección anti-bots documentadas; por defecto debe seguir desactivado.
  • Configura también las variables de proveedores externos que realmente uses (por ejemplo, los drivers y credenciales de RUC). No inventes tokens: cada valor secreto debe venir del proveedor correspondiente.

Desplegar y revisar migraciones

  1. Guarda la configuración y selecciona Deploy.
  2. El contenedor del rol app ejecuta al iniciar php artisan migrate --force, siembras base y luego inicia Nginx/PHP-FPM.
  3. Revisa los logs de despliegue. Si una migración falla, el arranque debe considerarse fallido: corrige la causa y vuelve a desplegar antes de publicar el frontend.
  4. La imagen instala PHP 8.3, Nginx y extensiones mediante paquetes binarios. No compila extensiones PHP con docker-php-ext-install ni PECL. Aun así, el tiempo de build depende de las descargas, Composer, red y caché del builder; no hay una duración garantizada.
En la configuración actual del backend, el rol app inicia Nginx/PHP-FPM y también los procesos scheduler/worker mediante Supervisor. No crees todavía aplicaciones duplicadas worker y scheduler: ejecutarían los mismos procesos más de una vez. Si se separan en recursos en el futuro, primero hay que ajustar y probar este modo de arranque.

7. Desplegar el frontend Astro

  1. En el mismo proyecto y ambiente, crea otra aplicación desde GitHub: EmersonValenzuela/consultashoyperu, rama main.
  2. Selecciona build por Dockerfile. El archivo está en la raíz del repositorio. Usa el puerto expuesto 80.
  3. Asigna el dominio público del frontend, por ejemplo https://consultasperu.safezoneperu.com.
  4. Configura los siguientes build arguments (también llamados argumentos de build o variables disponibles durante la compilación, según la pantalla de Coolify):
SITE_URL=https://consultasperu.safezoneperu.com
PUBLIC_API_URL=https://api-consultas.safezoneperu.com/api/v1

El Dockerfile del frontend usa esos valores al compilar Astro y luego sirve dist/ con Nginx. Si solo los agregas como variables disponibles en tiempo de ejecución, es posible que no cambien el sitio estático: confirma que Coolify los pase como build arguments y vuelve a desplegar después de modificarlos.

Usa como PUBLIC_API_URL el origen HTTPS público de la API más el prefijo /api/v1. La URL interna de PostgreSQL/Redis nunca debe incluirse en el frontend.

8. Validar frontend, API y conexiones

  1. Confirma que PostgreSQL y Redis aparecen healthy en Coolify antes de probar la API.
  2. Abre el dominio HTTPS de la API y consulta el health endpoint:
curl -i https://api-consultas.safezoneperu.com/api/v1/health

Verifica HTTP 200 y una respuesta JSON con estado saludable. Si responde 503 o la conexión falla, revisa los logs del backend y el health de las bases de datos.

  1. Abre el frontend por HTTPS y verifica que carguen las páginas y los assets.
  2. Prueba una pantalla que consuma la API y revisa Network/Console en el navegador. Confirma que las solicitudes vayan a https://api-consultas.safezoneperu.com/api/v1/..., no a localhost ni a una dirección privada.
  3. Revisa fallos de CORS: el origen del frontend debe estar incluido en CORS_ALLOWED_ORIGINS del backend. Después de cambiar variables de entorno, redepliega el recurso correspondiente.
  4. Confirma en el navegador que el certificado HTTPS es válido para ambos dominios.
  • DNS de frontend y API apunta a la IP correcta.
  • Puertos 80/443 alcanzan el proxy de Coolify.
  • PostgreSQL y Redis son privados y están healthy.
  • Las migraciones terminaron correctamente.
  • El health endpoint y una ruta del frontend responden por HTTPS.
  • El frontend consume la URL pública correcta de la API.

9. Respaldos y operación segura

  • Configura respaldos programados de PostgreSQL y guarda copias fuera del mismo VPS. Prueba la restauración antes de depender de ella.
  • Guarda de forma segura APP_KEY, credenciales de PostgreSQL/Redis y los secretos de instalación de Coolify. No los incluyas en Git, tickets públicos ni capturas.
  • Actualiza frontend/backend con despliegues nuevos y revisa sus logs. Mantén forma de volver a la versión anterior si un release falla.
  • Monitorea CPU, créditos burstable, RAM y espacio en disco. Los builds Astro/Composer pueden consumir CPU y espacio temporal para imágenes.
  • No elimines volúmenes de PostgreSQL/Redis al borrar o recrear aplicaciones. La vida del recurso/base de datos debe administrarse separada de la app.
  • Mantén APP_DEBUG=false en producción y restringe el acceso administrativo al panel Coolify.

10. Solución de problemas frecuentes

PostgreSQL: password authentication failed

Comprueba que DB_URL sea la URL interna exacta del recurso, el usuario y base existan y la contraseña corresponda al volumen ya inicializado. Cambiar la contraseña en Coolify no reescribe automáticamente credenciales de un directorio de datos existente. No borres el volumen para “probar”.

Connection refused / host no resuelto

Confirma que la aplicación, PostgreSQL y Redis estén en el mismo servidor/destino y red de Coolify, que las bases estén healthy y que la aplicación use las URLs internas. No reemplaces el host interno por localhost, la IP pública ni el nombre de otro recurso.

Frontend muestra errores CORS

Revisa CORS_ALLOWED_ORIGINS del backend, incluyendo protocolo HTTPS, dominio y ausencia de barra final. Cambia la variable y redepliega el backend.

Frontend llama a la API equivocada

Verifica PUBLIC_API_URL como build argument en el recurso frontend y vuelve a compilar/desplegar. Astro genera un sitio estático: no basta con cambiar una variable de runtime después de compilar.

El build tarda mucho o se agota

Revisa CPU, créditos, RAM y disco de la instancia. Despliega un recurso a la vez; el frontend compila con Node y el backend instala Composer/dependencias del sistema. Eliminar compilaciones de extensiones PHP reduce carga, pero no garantiza builds completos de menos de un minuto.

HTTPS no se emite

Confirma que DNS resuelva a este VPS, los puertos 80/443 estén abiertos y el dominio esté configurado en la aplicación antes de redeplegarla. Un DNS recién modificado puede tardar en propagarse.
